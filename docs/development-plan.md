# job-scout 开发计划书

> 版本 v1.0 ｜ 2026-10-28
> 目标读者：项目作者本人、面试官

---

## 1. 项目背景

### 1.1 问题

求职时最大的信息不对称是：**不知道市场到底要什么**。

- JD 散落在招聘平台上，看完就忘
- 靠感觉写简历，投出去石沉大海
- 想知道「实习岗到底要不要 LangGraph」，只能一个个翻

### 1.2 解法

把招聘数据变成**可检索、可问答、可量化**的资产：

```
采集真实岗位 → 结构化存储 → 可视化分析 → 自然语言问答 → 指导简历
```

### 1.3 与「普通 RAG Demo」的区别

| 维度 | 常见做法 | 本项目 |
|---|---|---|
| 数据 | 公开文档 / 造的数据 | **自己采集的 453 条真实 JD** |
| 评测 | 没有 | **33 条可复现评测集 + 多指标** |
| 优化 | 换模型 | **A/B 实验驱动，有对比数字** |
| 产品 | 一个聊天框 | **完整 Web 应用，含看板与调参** |

## 2. 用户与场景

### 2.1 主用户

求职者本人（找 Agent / 大模型方向的实习）。

### 2.2 核心场景

| 场景 | 用户输入 | 系统输出 |
|---|---|---|
| 技能侦察 | 「哪些实习岗要求 LangGraph？」 | 带引用的岗位列表 + 要求摘要 |
| 公司侦察 | 「安点科技在招什么？」 | 该公司全部岗位 + 技能分布 |
| 简历对照 | 「我会 Python 和 RAG，能投什么？」 | 匹配度排序 + 差距分析 |
| 市场分析 | （无需输入） | 看板：薪资/技能/方向分布 |

### 2.3 使用频率

低频、深度。每周 1–2 次，每次看几十条。

→ **不追求高并发，追求答案准确和可溯源。**

## 4. 系统架构

### 4.1 分层

```
┌──────────────────────────────────────────────┐
│  展示层  Next.js + TypeScript + Tailwind      │
│  概览 / 问答 / 列表 / 详情 / 看板 / 评测       │
└───────────────────┬──────────────────────────┘
                    │ REST + SSE
┌───────────────────▼──────────────────────────┐
│  服务层  FastAPI                              │
│  会话编排 / 流式输出 / 参数校验 / 错误处理      │
└───────────────────┬──────────────────────────┘
                    │ 函数调用
┌───────────────────▼──────────────────────────┐
│  RAG 层  Python（已有）                       │
│  语料 → 检索 → 融合 → 重排 → 生成 → 评测       │
└───────────────────┬──────────────────────────┘
                    │
┌───────────────────▼──────────────────────────┐
│  数据层  SQLite（岗位） + 向量索引文件         │
└──────────────────────────────────────────────┘
```

### 4.2 为什么这样分

| 决策 | 理由 |
|---|---|
| 前端独立于后端 | 前端可独立迭代 UI，后端 API 稳定 |
| RAG 层独立成库 | 已被 CLI 和 Web 复用，将来可换前端 |
| SQLite 而非 Postgres | 数据量 453 条，SQLite 零运维 |
| 向量存文件而非向量库 | 同量级下无需引入 Milvus/Chroma |

### 4.3 关键设计原则

1. **结构化字段优先**：标题/公司/技能是免费的高质量信号，先于正文
2. **一条 JD 一个 chunk**：不按 token 硬切，保留语义完整性
3. **所有优化必须有评测支撑**：没数字的改动不上线
4. **生成必须带引用**：没有引用的答案视为无效

## 5. 核心流程

### 5.1 索引流程（离线，一次性）

```
453 条岗位（SQLite）
   │
   ├─ 读取：标题 / 公司 / 城市 / 技能 / 正文
   │
   ├─ 组装检索文本（结构化字段 + 正文）
   │
   ├─ 分词（jieba + 英文技术词保留）
   │
   └─ 建索引
        ├─ BM25 倒排
        └─ 向量索引（bge-small-zh）
```

产出：`index/bm25.pkl` + `index/vectors.npy` + `index/meta.json`

### 5.2 问答流程（在线，每次请求）

```
用户问题
   │
   ├─ 1. 查询改写（多轮时）
   │      「那它要几年经验？」→「星云深图 AI Agent 实习要几年经验？」
   │      自包含问题直接跳过
   │
   ├─ 2. 双路召回
   │      ├─ BM25：精确匹配专有名词（LangGraph、MCP）
   │      └─ 向量：语义匹配（「调外部接口」≈「Function Calling」）
   │
   ├─ 3. RRF 融合
   │      按排名倒数加权合并两路结果，无需调分数尺度
   │
   ├─ 4. 自适应重排
   │      Top1 与 Top2 分差 > 阈值 → 跳过 rerank（省延迟，指标不降）
   │      分差小 → 调用 rerank 精排
   │
   ├─ 5. 上下文组装
   │      取 Top-N 片段，按字符预算截断（不按条数）
   │      编号 [1][2][3] 供引用
   │
   ├─ 6. 生成（流式）
   │      提示词要求：只依据给定片段、必须标注引用编号、
   │      信息不足时明确说「没有找到」
   │
   └─ 7. 后处理
          解析引用编号 → 关联岗位元数据 → 推给前端
```

### 5.3 评测流程

```
评测集（33 条，规则合成）
   │
   ├─ 三类型：技能查询 / 公司查询 / 区域查询
   │
   ├─ 分别跑检索
   │
   ├─ 计算指标
   │      ├─ 技能类（答案多）→ Precision@10
   │      └─ 公司/区域（答案少）→ Recall@10 + MRR
   │
   └─ 输出：对比表 + 失败样例
```

**关键决策**：不同查询类型用不同指标。原因是「哪些岗位要 Python」有 118 个正确答案，`Recall@10` 上限只有 0.085，用它评价不公平。

## 7. 技术选型

| 层 | 选择 | 理由 | 备选 |
|---|---|---|---|
| 前端 | Next.js + TS | 全栈履历，SSR 友好 | Vue / 原生 HTML |
| 样式 | Tailwind | 快速、一致 | CSS Module |
| 后端 | FastAPI | 异步、OpenAPI 自动文档 | Flask |
| 检索 | BM25 + 向量 | 互补：精确 vs 语义 | 纯向量 |
| 向量模型 | bge-small-zh | 中文、小（95MB）、本地免费 | OpenAI embedding |
| 生成 | DeepSeek | 便宜、兼容 OpenAI SDK | 本地 Ollama |
| 存储 | SQLite + 文件 | 零运维 | Postgres + pgvector |
| 部署 | Docker Compose | 3 容器，一键起 | 裸机 |

### 7.1 关键权衡

**为什么不用向量数据库？**
453 条数据，暴力检索毫秒级。引入 Chroma/Milvus 只会增加运维成本，不带来收益。数据涨到 10 万条再考虑。

**为什么保留 BM25？**
岗位检索里「LangGraph」「MCP」这类专有名词，BM25 比向量准。评测也证明：混合优于单路。

### 11.3 M1 结果：混合检索（2026-10-28）

语料 199 篇实习 JD，评测集 33 条（技能 12 / 公司 12 / 区域 9）。

| 配置 | Recall@1 | Recall@5 | Recall@10 | Precision@10 | MRR |
|---|---|---|---|---|---|
| BM25 | 0.168 | 0.521 | 0.578 | 0.609 | 0.864 |
| 向量（bge-small-zh） | 0.106 | 0.297 | 0.367 | 0.430 | 0.760 |
| **RRF 融合** | 0.146 | 0.448 | 0.533 | **0.645** | **0.962** |

**按查询类型（融合配置）**

| 类型 | 数量 | Recall@10 | Precision@10 | MRR |
|---|---|---|---|---|
| 技能 | 12 | 0.152 | **1.000** | **1.000** |
| 公司 | 12 | 0.853 | 0.375 | 0.958 |
| 区域 | 9 | 0.615 | 0.533 | 0.917 |

**结论**

1. **MRR 0.864 → 0.962（+11.3%）**，超过验收标准的 +5%
2. **向量单独用不如 BM25**（0.760 vs 0.864）——查询以专有名词为主，词法匹配更准
3. **融合提升排序质量，但牺牲部分召回**：Recall@10 从 0.578 降到 0.533，因为两路结果混合后，部分正确答案被挤出 Top-10
4. **技能类查询达到完美**：Precision@10 = 1.0、MRR = 1.0

**自适应重排：框架完成，策略负优化**

第四组配置对比（重排器为 LLM listwise，因 HuggingFace 大文件限流无法下载 cross-encoder）：

| 配置 | Recall@10 | Precision@10 | MRR |
|---|---|---|---|
| RRF 融合 | 0.533 | 0.645 | **0.962** |
| +自适应重排(LLM) | 0.465 | 0.606 | 0.892 |

**结论：重排让指标变差 7.3%。** 这是真实的负优化，不是 bug。

原因分析：
1. 每条候选只给 LLM 看前 180 字，看不到完整岗位要求
2. listwise 排序 20 条候选对模型来说太长，容易乱序
3. 融合排序本身已经很准（MRR 0.962），提升空间小、破坏风险大

路由本身工作正常：26/33 条触发重排，7 条因分差大跳过。

**改进方向**（未做）：
- 换 cross-encoder（`bge-reranker-base`），精度高且不吃上下文
- 提高阈值，只对分差极小的查询重排
- 给 LLM 更完整的候选上下文（成本上升）

> 调试插曲：第一版重排结果与融合完全一致，查出来是 `_build_prompt` 里一行残留代码
> 导致每次调用都抛 NameError，被 try/except 吞掉后静默回退原顺序。
> ruff 的 F821 抓到了它。**异常静默吞掉会让负优化伪装成"无效果"。**

### 11.4 下一步

### 11.5 M2 生成层：已完成（2026-10-28）

Key 到位后完成验收。

| 指标 | 结果 | 验收标准 |
|---|---|---|
| 忠实度 | **93.1%（27/29）** | ≥85% ✅ |
| 带引用的回答 | 29/29 | — |
| 单次生成耗时 | 约 3s | — |
| 拒答机制 | 无检索结果时明确说没有 | ✅ |

**调试记录（比结果更有价值）**

| 轮次 | 忠实度 | 原因 |
|---|---|---|
| 1 | 83.3% | 真实的措辞升级（参与→负责） |
| 2 | 75.0% | 加了提示词反而降，开始怀疑评测 |
| 3 | 62.1% | 扩大样本到 30 条，问题更明显 |
| 4 | **93.1%** | 修掉两个评测 bug |

两个评测 bug：

1. **上下文截断**：`body = desc[:1200]`，但最长 JD 有 3245 字。
   模型引用的内容在 context 里根本不存在，被判成幻觉。
2. **judge 又截断一次**：judge 的 prompt 里写了 `context[:3000]`，
   而 context 实际有 12000 字，后几条片段 judge 根本没看到。

**结论：指标异常时先查评测管线，不要急着怪模型。**

修复后剩余的 2 条不忠实是「过度概括」（如称「RAG 只出现在 [2] 的任职要求」，
实际 [1] 也有），属于可接受误差。

原来要分四步：起 serve → 开浏览器 → 点两下按钮 → 单独生成看板。

1. 检查端口，必要时在后台线程起接收服务
2. 拼 URL（带 `?jobscout=auto`）并打开默认浏览器
3. 油猴脚本 v0.8.0 检测到标记 → 4 秒后自动滚动
4. 滚动结束 → 自动接上 JD 抓取（`stopAuto` 钩子）

6. 自动生成看板并打开

- 标记存 localStorage，登录跳转后仍生效
- 手动点停止会 `setAutoRun(false)`，不会自己又跑起来
- 终端有超时兜底（默认 40 分钟）
- 兜底判断：岗位数稳定 3 分钟且无待抓正文

**未实测项**：`webbrowser.open` 自动打开浏览器的实际效果未在本次验证
（会弹窗打扰用户），只验证了 URL 拼接与后续流程。

### 11.11 JD 抓取改走 JSON 接口（2026-10-29）

**问题**：JD 抓到第 5 条左右就撞人机校验。

**根因**：不是频率，是**请求特征**。旧实现 `fetch(详情页URL)` 拉整页 HTML
再用 DOMParser 解析，而正常用户打开详情页是「点击 → 导航 → 页面自己发 XHR
拿 JSON」。从列表页用 XHR 拉整页 HTML，对风控模型是明显异常。

**方案**：改调详情接口

```
GET /wapi/zpgeek/job/detail.json?encryptJobId=xxx&securityId=xxx
```

来源：社区维护的 [boss-agent-cli 接口定义](https://raw.githubusercontent.com/can4hou6joeng4/boss-agent-cli/refs/heads/master/src/boss_agent_cli/api/boss.yaml)，
标注 `effect: read`、`replay_safe: true`。同一份文档给出了完整风控码：

| code | 含义 |
|---|---|
| 9 | 频率限制 |
| 31 | IP 限制 |
| 32 | 账号限制 |
| 36 | 账号风险 |
| 37 | 登录过期 |

（原实现只认 31 / 37。）

**改动**（油猴脚本 v0.9.0）

| 改动 | 说明 |
|---|---|
| 接口优先 | `fetchOneJDApi()` 调 detail.json |
| 字段自适应 | 结构不确定时深度搜索最长字符串 |
| HTML 兜底 | 接口走不通才回退整页 HTML |
| 风控识别 | 5 个码全认，**连续 2 次就停**（原 6 次） |
| 自诊断 | 首次字段解析失败上报真实 JSON 到 `/debug` |
| 测试按钮 | 「测试详情接口（不占额度）」只发 1 个请求 |

**验证**

用户实测：`接口可用！抓到 1250 字：岗位职责 1、AI 产品设计与原型开发…`

**后续观察**：连续抓取能撑多少条还没跑满，需要实际采集验证。
若接口也被限，Plan B：拉长间隔（10–20s + 抖动）、分批（20 条/轮）、
换源（实习僧）、只抓高价值岗位。

### 11.12 每日增量更新（2026-10-29）

**新需求**：每天自动更新，关注岗位时效性；可以慢，一小时内跑完即可。

**调研**（增量爬虫的通用做法）：

| 来源 | 要点 |
|---|---|
| [Incremental Crawling](https://www.scrapecrew.com/glossary/incremental-crawling) | 唯一键去重 + 时间戳 + 只重抓变化部分 |
| [Re-Crawl Only What Changed](https://guides.proxiesapi.com/posts/incremental-web-scraping-recrawl-only-what-changed) | 用 `last_seen` / 内容 hash 判断下架 |
| [增量 RAG 索引](https://zh-cn.crawlbase.com/blog/incremental-rag-index-with-crawler-webhooks-and-pgvector/) | 增量更新时避免全量重建索引 |

三要素：唯一键去重、时间戳、变更检测。前两个我们早就有
（`dedupe_key` + `first_seen/last_seen`），缺的是「本轮没出现 = 停招」。

**实现**

| 组件 | 内容 |
|---|---|
| `Storage.mark_stale(days)` | `last_seen < cutoff` 且 `is_active=1` → 标记停招 |
| `Storage.daily_stats(since)` | 新增 / 停招 / 在架 / 有 JD |
| `job-scout daily` | 起服务 → 开浏览器 → 采列表 → 导航模式抓 JD → 标停招 → 出日报 |
| `install-daily-task.ps1` | 注册 Windows 计划任务，每天定时跑 |

**关键坑：阈值不能短**

实测发现默认 3 天会误伤 189 条：

```
last_seen 分布：
  10-29（今天）: 549 条
  10-23（6天前）: 187 条   ← 别的关键词/城市采的，今天没跑
```

因为单次 `daily` 只跑一个关键词+城市，其他查询的岗位不会刷新。
阈值改成 **7 天**，实测 0 条误伤。

**daily 执行链路**

```
起 8765 服务 → webbrowser.open(带 jobscout=auto)
→ 脚本自动滚动采列表
→ 滚动结束自动切「导航模式」抓 JD（真导航，风控低）
→ 抓完 POST /auto-done
→ CLI 感知完成 → mark_stale → 日报 → 生成看板
```

**验证**

```
$ job-scout daily --no-open --timeout-min 0 --no-dashboard

═══ 今日日报 ═══
  新增岗位    0
  标记停招    0 条（7 天没出现）
  在架岗位    738
  有 JD 正文  476
```

**尚未验证**：真实的每日全流程（需要浏览器登录态 + 实际跑一小时）。

### 11.13 数据清理与相关性过滤（2026-10-29）

**问题**：全部实习岗 445 条里，65% 是「产品实习生」「视觉设计」「游戏策划」这类，

```

  相关 371 / 无关   371
  有 JD 622 / 无 JD  120
```

| 层 | 规则 | 实现 |

`--rerank` 改为显式开启，默认关闭。评测耗时从几分钟降到 **4 秒**。
